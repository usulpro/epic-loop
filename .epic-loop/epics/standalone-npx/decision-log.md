# Decision Log

## Active Decisions

- **Package location**: `packages/cli` inside this repo, not a separate repository.
- **No pnpm workspace**: `packages/cli` is a self-contained npm package with its own `package.json` and its own install, not a formal pnpm workspace member. Reason: the repo root is a private plugin/skill distribution, not a code package, so there is currently no second package to justify workspace tooling (shared deps, `workspace:*` protocol, hoisting). Revisit only if a genuine second package or shared-dependency need appears later.
- **Package name**: `epic-loop`, published publicly to npm. Confirmed available on the registry (`npm view epic-loop` returned 404) as of 2026-07-04.
- **Publish model (Phase 2)**: manual `npm publish`, executed by the user themselves. No CI-based release automation in this epic's scope. Status: done — user published `epic-loop@0.1.0` to the public npm registry on 2026-07-04 and confirmed with a real `npx epic-loop` invocation.
- **Starting language**: plain JavaScript (ESM), matching the rest of the repo. Explicitly not a hard constraint — Phase 3 may adopt TypeScript if the chosen CLI/TUI stack benefits from it; that move is not to be treated as scope creep or a later "reset."
- **Dependency policy**: `packages/cli` may take on npm runtime dependencies (CLI parsing, output styling, TUI libraries). This differs from the skill's own `scripts/*.mjs` convention (Node built-ins only) — that convention applies to the skill scripts, not to this published package.
- **Phase 5 / eval-metrics coordination**: coordinate with the existing `test-coverage` epic instead of building an independent eval-fixture harness. `test-coverage`'s Phase 2 (not yet started) already targets an eval-fixture pipeline; this epic's Phase 5 reuses/extends that work rather than duplicating it. Exact coordination mechanics (ownership, hand-off point) to be worked out when Phase 5 actually starts.
- **Roadmap shape**: Phase 1 is the standard "shape the epic" phase; the user's four described phases became Phases 2-5 — (2) bootstrap + zero-arg status command + manual publish, (3) CLI/TUI stack research with competing prototypes and a user-reviewed pick, (4) full user command surface research/spec/implementation/testing, (5) skill migration from scripts to CLI with before/after eval metrics driving an adopt/drop/iterate decision.

- **Implementation run scope (2026-07-04)**: user explicitly started the implementation loop but scoped this session to Phase 2 only ("run implementation loop but only do the first phase, then stop"). techlead must not advance into Phase 3 after Phase 2 closes; set `next_role idle` after Phase 2's phase-closure housekeeping instead.

## Distribution Foundation (2026-10-02, direct user session, outside the loop)

Decided with the user and implemented in the same session; deliberately not added as roadmap tasks. Remaining tasks were adjusted to build on it.

- **Skill ↔ CLI invocation contract**: the skill reaches the CLI only through a thin wrapper, `<skill-dir>/scripts/epic-loop.mjs`, which runs `npx --yes --prefer-offline epic-loop@<SKILL_VERSION>` with `EPIC_LOOP_SKILL_DIR` (its own directory) in the env. cwd is never changed: it is the project root. Rejected: passing `--skill-dir` on every call (agent error-prone, verbose); bundling the skill's `scripts/lib` into the CLI with esbuild (user decision: no build-time absorption of skill code; the CLI itself is still built before publish). Why a skill dir at all: the CLI runs from the npx cache, but hook commands, templates, and role-prompt reference paths all point into the installed skill.
- **One version**: skill, both plugin manifests, root package, and the npm CLI share one version. The wrapper's `SKILL_VERSION` is the pin; `scripts/release.mjs` stamps it everywhere; `pnpm run validate` fails on drift; the CLI build refuses to run if wrapper and package versions differ. Consequence: a skill copy always runs exactly the CLI it was released with, so the two cannot diverge by construction.
- **Measured npx overhead** (from uRec, 2026-10-02): direct `node` script ~30 ms; `npx epic-loop` unpinned ~500 ms (registry round-trip, 5 s cold); `npx --prefer-offline epic-loop@<exact>` ~270 ms with no network after first fetch. Pinned + `--prefer-offline` is the wrapper default. This matters for Phase 5 if hooks move behind the wrapper (3 hook events per turn).
- **Dev override**: `EPIC_LOOP_CLI=<path to packages/cli/src/cli.mjs>` makes the wrapper (and CLI-internal re-invocations) run local source instead of npm. Used by unit tests and when exercising unreleased CLI changes.
- **Supported install types**: (1) manual copy of the skill folder; (2) Codex or Claude Code plugin via marketplace; (3) `npx epic-loop install --platform <p>`, which produces the same end state as (1) plus hooks. Claude Code plugin/marketplace manifests were missing despite README claims and were added (`plugins/epic-loop/.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`).
- **The npm package ships the skill**: the build copies `plugins/epic-loop/skills/epic-loop` into `packages/cli/skill/` (gitignored), so `install`/`update` source the skill from the same tarball as the CLI.
- **Update paths**: local copies (1, 3) update via `npx epic-loop@<latest> update`, an atomic in-place swap (staging dir + rename; keeps a `.runtime/` if present). Local edits to a copied skill are not supported and are overwritten. Plugin installs (2) update only through the host (`claude plugin marketplace update` + `claude plugin update`; `codex plugin marketplace upgrade` + `codex plugin add`); the CLI only prints those commands. After a plugin update, doctor must be rerun because the versioned plugin cache path changes and the hook command goes stale.
- **Update check**: doctor queries `registry.npmjs.org/epic-loop/latest` at most once per day per project (cache `.epic-loop/.runtime/update-check.json`, 2 s timeout, offline = "not checked", never a failure). npm `latest` is the single source of truth for all install types because versions move in lockstep.
- **Autoupdate**: machine-local `autoupdate` in `.epic-loop/.runtime/config.json` (default false; `epic-loop config set autoupdate true`). When on, doctor updates a local copy without asking, then re-executes itself through the updated wrapper so state compatibility repairs run under the new version, and reports `update.action: "applied"` (SKILL.md tells the agent to re-read SKILL.md). Plugin installs are never auto-updated.
- **First migrated command: `doctor`**: lives in `packages/cli/src/doctor/` with a deliberate, temporary duplicate of the lib it needs (`common` subset, `hook-config` parameterized by skill dir, `hook-compatibility`, initial roadmap state). The skill's own `scripts/doctor.mjs` and lib stay until Phase 5 removes the duplication. SKILL.md and references now call doctor through the wrapper.
- **Release model**: still a manual `npm publish` by the user; everything around it is scripted in `scripts/release.mjs` (`prepare` → manual `npm publish` → `wait` → `finish`, plus `abort`) and driven end-to-end by the repo-local `/release-epic` Claude Code skill (`.claude/skills/release-epic/`, committed via a narrow `.gitignore` exception). `prepare` only commits locally; `finish` pushes only after npm serves the version and an `npx` smoke test passes, then syncs and verifies the runtime skill copies. Order is mandatory: the skill on `main` pins the new version, so npm must have it first. Planned: move publishing to CI, so a release becomes "push a version tag".
- **"No pnpm workspace" still holds**: `packages/cli/pnpm-workspace.yaml` exists only because pnpm 11 keeps settings there (`allowBuilds: esbuild: true`, required for `prepack`); it declares no workspace packages.
